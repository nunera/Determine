# Determine wire protocol v2

Single source of truth for every byte exchanged between the two wearable boards and the phone. Implementations:

| Language | File | Used by |
|---|---|---|
| Python (reference) | `protocol/python/determine_wire.py` | simulator, golden vectors |
| C | `firmware/common/include/determine_wire.h` | cue board, camera board |
| Kotlin | `phone/core/src/main/kotlin/.../wire/` | phone core, Android app |

Golden vectors (`protocol/vectors/vectors.json`) are generated by the Python reference (`protocol/gen_vectors.py`). Every other implementation MUST decode each vector to the listed fields and re-encode it to the identical bytes.

**What changed in v2** (from v1): the cue board wears ONE forward single-zone ToF (Arduino Modulino Distance, VL53L4CD) — `RANGE` is a single scalar reading, no 8×8 grid, no resolution field, no mounting transform. The board no longer makes sound at all: CUE carries only haptic fields (no gains), ACK no longer reports applied gains, PROFILE is `mode` + `haptic_max`. All audio is synthesised by the phone and sent to the bone-conduction Bluetooth headset; a failing phone audio route MUST be reported explicitly, never silently redirected to the speaker. Header `ver` is `2`. Everything else (transport, BEAT, FRAME, PING/PONG, clocks, cue IDs, haptic patterns, watchdog timing) is unchanged from v1.

## Transport

- UDP over the phone's Wi-Fi hotspot. All integers **little-endian**. No padding.
- Phone listens on **47000**. Cue board (XIAO ESP32-C3) listens on **47001**. Camera board (ESP32-CAM) listens on **47002**.
- Boards send to their DHCP gateway (the phone hotspot) on port 47000. The phone learns each board's IP from its first packet.
- Clocks: board time is `esp_timer_get_time()` in µs since boot. Phone time is its monotonic clock in µs.

## Header (8 bytes, every packet)

| Offset | Field | Type | Notes |
|---|---|---|---|
| 0 | magic | u16 | `0x5444` (bytes `44 54`, "DT") |
| 2 | ver | u8 | `2` |
| 3 | type | u8 | see below |
| 4 | seq | u32 | per-sender counter, wraps. Board packets: per type. **Phone → cue board commands (CUE and PROFILE) share ONE counter** so every ACK maps to exactly one command; receivers must not assume consecutive seqs |

Receivers drop packets with wrong magic, wrong version, unknown type or wrong length.

## Types

| Type | Name | Direction | Body bytes | Total |
|---|---|---|---|---|
| 0x01 | BEAT | board → phone | 16 | 24 |
| 0x02 | RANGE | cue board → phone | 11 | 19 |
| 0x03 | FRAME | camera board → phone | 30 + chunk_len | ≤ 1438 |
| 0x10 | PING | phone → board | 8 | 16 |
| 0x11 | PONG | board → phone | 24 | 32 |

| 0x21 | ACK | cue board → phone | 14 | 22 |

### BEAT 0x01 — 10 Hz from each board

| Field | Type | Notes |
|---|---|---|
| board | u8 | 1 = CAM, 2 = CUE |
| reset_reason | u8 | `esp_reset_reason()` value at boot |
| faults | u16 | bit flags, below |
| t_us | u64 | board time at send |
| rssi_dbm | i8 | Wi-Fi RSSI |
| temp_c | i8 | 127 = unknown |
| heap_kb | u16 | free heap |

Fault bits: 0 SENSOR_INIT_FAIL · 1 SENSOR_READ_ERR · **2 reserved (was I2S_ERR; the board has no audio in v2 and MUST send 0)** · 3 HAPTIC_L_ERR · 4 HAPTIC_R_ERR · 5 BROWNOUT_SEEN · 6 NO_CLOCK_SYNC · 7 WATCHDOG_ACTIVE · 8 LOW_HEAP · 9 CAPTURE_FAIL.

### RANGE 0x02 — 15 Hz from the cue board, ONE forward reading

| Field | Type | Notes |
|---|---|---|
| t_us | u64 | board time when the sensor reported |
| mm | u16 | forward distance; **0 unless status = VALID** |
| status | u8 | canonical, below |

The cue board wears one Arduino Modulino Distance (VL53L4ED on the purchased unit): a single forward-looking zone (~18° diagonal FOV, vendor maximum range up to 1.2 m; usable warning distance unvalidated). This is a staged near-field demo, not a 3 m grid and not a lateral sensor: one zone cannot tell left from right, cannot resolve multiple objects, and MUST never be associated with an arbitrary camera object.

Canonical status:

| Value | Name | Meaning |
|---|---|---|
| 0 | VALID | trustworthy distance in `mm` |
| 1 | NO_TARGET | the sensor reported no target within range (signal below threshold, or beyond range); **not** "clear" |
| 2 | UNKNOWN | reading unusable (invalid, wrap-around, saturated, sensor error) |

The board maps the raw VL53L4ED `range_status` as follows (`dt_range_status_from_tof` in `firmware/cue-board/lib/cue_logic`): `0` → VALID; `2` (signal below threshold, no target) and `4` (phase out of limits, beyond range) → NO_TARGET with `mm = 0`; every other raw status (wrap-around, saturation, sigma or minimum-range failures) and every read error → UNKNOWN with `mm = 0`. The simulator uses the same mapping: no return in view or beyond the 1200 mm limit is NO_TARGET, while explicit glass/saturation fixtures stay UNKNOWN. NO_TARGET means only that the sensor reported no target within range — it is **still not clear**: it licenses no speech, no cue and no reassurance (the phone stays quiet; READY is permitted but is not an all-clear). Only VALID carries a distance; UNKNOWN stops metric warning repeats and enters announced DEGRADED, including startup once the links and outputs are confirmed. Nothing licenses an "all clear".

### FRAME 0x03 — JPEG in chunks

| Field | Type | Notes |
|---|---|---|
| frame_id | u32 | increments per frame |
| t_cap_us | u64 | board time of capture |
| w | u16 | pixels |
| h | u16 | pixels |
| total_len | u32 | JPEG bytes |
| offset | u32 | of this chunk |
| chunk_len | u16 | ≤ 1400 |
| chunk_idx | u16 | 0-based |
| chunk_count | u16 | |
| data | u8[chunk_len] | |

The phone drops any frame not complete within 150 ms of its first chunk, and any frame older than the freshness bound. Camera objects describe the scene; the single ToF zone is the only range source and is never fused with a camera object by identity.

### PING 0x10 / PONG 0x11 — clock sync, 10 Hz per board

PING: `t_phone_us u64`. PONG: `t_phone_us u64` (echo), `t_board_rx_us u64`, `t_board_tx_us u64`.

Phone computes (NTP-style), with `t4` = phone receive time:
`offset = ((rx − t_phone) + (tx − t4)) / 2` (board − phone), `rtt = (t4 − t_phone) − (tx − rx)`. Keep the offset from the lowest-RTT sample in a sliding window.

PING also serves as the phone's liveness signal to the cue board (watchdog).

### CUE 0x20

| Field | Type | Notes |
|---|---|---|
| t_issued_phone_us | u64 | phone time at send (logging) |
| deadline_board_us | u64 | phone's estimate of board time at issue + ttl; **0 = no sync** |
| cue_id | u8 | table below (the phone's sound semantics) |
| side | u8 | 0 L, 1 R, 2 BOTH — gates the temple haptic channels only |
| haptic_pattern | u8 | table below |
| haptic_l | u8 | 0–255 intensity, clamped to `profile.haptic_max` by the board |
| haptic_r | u8 | 0–255 intensity, clamped to `profile.haptic_max` by the board |
| flags | u8 | bit0 = interrupt the current haptic output |
| ttl_ms | u16 | advisory/logging; the deadline already includes it |

The board is **haptic-only**: it plays `haptic_pattern` at the given intensities (per `side`) on its haptic hardware, nothing else. The current bench board has one Modulino Vibro, so it plays `max(haptic_l, haptic_r)` on that single motor and cannot lateralise; the wire format still carries both sides. `cue_id` is carried for the phone's audio semantics — the phone synthesises the sound itself and repeats cues with one CUE per repetition.

The cue board drops a CUE if `deadline_board_us == 0` or `now > deadline_board_us` (ACK NO_SYNC / EXPIRED). It clamps each haptic intensity to `profile.haptic_max` (ACK APPLIED_CLAMPED when clamping changed a value). Obstacle cues derived from the single forward zone are always side BOTH — one zone never implies left or right.

### ACK 0x21

`cue_seq u32` (the CUE or PROFILE header seq; unique because the phone draws both from one counter), `status u8`, `reserved u8` (0), `t_board_us u64`.

| status | Name | Meaning |
|---|---|---|
| 0 | APPLIED | command executed |
| 1 | EXPIRED | past `deadline_board_us` at the board |
| 2 | APPLIED_CLAMPED | executed with a haptic intensity clamped to `haptic_max` |
| 3 | NO_SYNC | `deadline_board_us == 0` |
| 4 | BAD_CUE | unknown cue id / side / pattern, or unknown PROFILE mode |
| 5 | BUSY_DROPPED | haptic output busy and the interrupt flag not set |

### PROFILE 0x22

`mode u8`, `haptic_max u8`. `mode` keeps the phone's audio-profile enum — 0 STEREO, 1 SSD, 2 HAPTIC_ONLY — for the phone's own semantics; the board is always haptic-only and does not change behaviour with it. `haptic_max` MUST be **1–255**: it is the ceiling the board clamps CUE `haptic_l`/`haptic_r` to, and it also sets the watchdog LSS intensity. A minimum of 1 keeps the haptic channel from being configured away — with no board audio, the watchdog LSS is the last failure channel local to the board — but 1 is only the lowest legal setting, **not** a guarantee that the vibration is perceptible (that depends on actuator, contact and wearer, and is characterised on the bench). Acknowledged with ACK APPLIED; an unknown `mode` or `haptic_max == 0` is ACK BAD_CUE and the previous profile stays in force. The phone MUST NOT send `haptic_max == 0` (it constrains its own setting to ≥ 1 and explains why it cannot disable this channel); stopping/pausing the system remains a separately defined phone action.

## Cue IDs

The IDs keep the phone's sound semantics; the sounds are synthesised by the phone and played over the bone-conduction Bluetooth headset (the board only vibrates):

| ID | Name | Phone sound |
|---|---|---|
| 0 | READY | one soft tick |
| 1 | OBSTACLE_FAR | wood-block double |
| 2 | OBSTACLE_MID | wood-block double |
| 3 | OBSTACLE_NEAR | one sharper urgent note |
| 4 | PERSON_FAR | two-tone marimba rising |
| 5 | PERSON_MID | two-tone marimba rising |
| 6 | PERSON_NEAR | one sharper urgent marimba note |
| 7 | SYSTEM_OFF | three descending notes |
| 8 | CAL_TONE_500 | 300 ms 500 Hz tone |
| 9 | CAL_TONE_1K | 300 ms 1 kHz tone |
| 10 | CAL_TONE_2K | 300 ms 2 kHz tone |
| 11 | CAL_OBSTACLE | wood-block double (balance step) |

Timing rule (Arch §8.1): every note ≥ 83 ms; whole cue fits its repetition period with a ≥ 100 ms gap; ≤ 6 notes/s.

## Haptic patterns

0 NONE · 1 PULSE40 (40 ms) · 2 PULSE60 (60 ms) · 3 BUZZ150 (150 ms) · 4 LSS (400 ms on, 100 off, 120 on, 100 off, 120 on).

## Watchdog

The cue board enters WATCHDOG when no PING arrives for 800 ms (or none within 5 s of boot). It then plays haptic LSS (at `profile.haptic_max`, which is always ≥ 1, on both temples) every 5 s and sets fault bit 7, until PINGs resume. The board makes no sound; the phone announces the lost board itself, and its own audio-route failure must be explicit (never a silent speaker fallback).

## Hazard bands (near-field demo policy)

Conservative, measured/tunable on the bench; the vendor maximum range is up to 1.2 m (usable warning distance unvalidated), so no band reaches beyond it:

| Band | Range | Cue |
|---|---|---|
| FAR | 900–1200 mm | OBSTACLE_FAR / PERSON_FAR |
| MID | 500–899 mm | OBSTACLE_MID / PERSON_MID |
| NEAR | < 500 mm | OBSTACLE_NEAR / PERSON_NEAR |
| — | > 1200 mm or NO_TARGET | no obstacle claim (quiet; never "clear") |
| — | UNKNOWN | announced failure; never a distance, never "far" |

There is **no all-clear**: no cue, speech or vibration may ever assert that the path is clear. Failures (sensor fault, lost board, no clock sync) are always announced.
